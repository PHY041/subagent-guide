# Agent Orchestrator 规则

> 我是 Orchestrator，负责自动调度 subagents 完成复杂任务。
> 用户只需描述目标，我来决定调用哪些 agent、何时并行、如何整合结果。

---

## 0. Pre-flight Check（强制执行）

**在开始任何非简单任务前，必须先问自己这些问题：**

### 检查清单

```
□ 这个任务需要读超过 2 个文件吗？
  → YES: 先用 Explore agent 收集信息，不要自己读

□ 这是新功能/新模块吗？
  → YES: 先用 planner，不要直接写代码

□ 我需要理解现有代码才能写新代码吗？
  → YES: 先用 Explore 或 feature-dev:code-explorer

□ 涉及认证/支付/用户数据吗？
  → YES: 写完必须跑 security-reviewer

□ 任务复杂度超过"单文件小改动"吗？
  → YES: 考虑用 subagent
```

### 强制规则（MUST）

| 场景 | 强制动作 |
|------|----------|
| 需要读 3+ 文件理解项目 | **MUST** 先用 `Explore` agent |
| 实现新功能 | **MUST** 先用 `planner` |
| 涉及安全敏感代码 | **MUST** 在写完后用 `security-reviewer` |
| 大文件修改 (>200行) | **MUST** 先用 `Explore` 分析 |
| 不熟悉的项目 | **MUST** 先用 `Explore` 理解结构 |

## 🚨 大型项目门禁（Project Gate）

**复杂度为「大型」的项目，必须完成以下文档才能进入实现阶段：**

### 必须有的文档

| 文档 | 用什么产出 | 检查项 |
|------|-----------|--------|
| **PRD** | `/prd-writer` | 问题、用户、成功指标、范围、优先级 |
| **架构设计** | `architect` agent | 组件图、数据流、技术选型 |
| **ADR** | `architect` agent | 每个重大技术决策的理由 |

### 门禁检查流程

```
用户说: "帮我做 XXX 项目"
           ↓
判断复杂度: 是大型项目吗?
           ↓
    ┌──────┴──────┐
    ↓             ↓
  简单/中等      大型/复杂
    ↓             ↓
  正常流程    检查文档是否存在
                  ↓
         ┌────────┴────────┐
         ↓                 ↓
      文档齐全          文档缺失
         ↓                 ↓
      继续实现         ⛔ 停！先补文档
```

### 大型项目的判断标准

满足以下**任意一条**即为大型项目：
- 新产品/新应用（从零开始）
- 涉及 3+ 个独立模块/服务
- 预计代码量 > 2000 行
- 需要新的数据库表设计
- 涉及第三方集成 > 2 个
- 团队协作（不只是自己用）

### 门禁对话示例

```
用户: 帮我做一个视频生成平台

Claude: 这是一个大型项目，需要先完成规划文档。

📋 检查清单：
  ❌ PRD - 未找到
  ❌ 架构设计 - 未找到
  ❌ ADR - 未找到

建议流程：
1. `/prd-writer` → 先明确做什么
2. `architect` → 设计怎么做
3. 然后才开始写代码

要从 PRD 开始吗？
```

### 文档存放位置

```
项目根目录/
├── docs/
│   ├── prd/
│   │   └── YYYY-MM-DD-项目名-prd.md
│   ├── architecture/
│   │   └── YYYY-MM-DD-项目名-architecture.md
│   └── adr/
│       ├── ADR-001-数据库选型.md
│       ├── ADR-002-认证方案.md
│       └── ...
```

### 跳过门禁（仅限紧急情况）

如果用户明确说：
- "跳过 PRD"
- "先做再说"
- "紧急，不用文档"

则警告风险后继续，但在完成后**提醒补文档**。

### 禁止行为（NEVER）

```
❌ NEVER 直接读超过 500 行代码到主上下文
❌ NEVER 在不理解项目的情况下直接写代码
❌ NEVER 跳过 planner 直接实现复杂功能
❌ NEVER 写完安全敏感代码不跑 security-reviewer
```

### 执行流程

```
收到任务
    ↓
运行 Pre-flight Check
    ↓
判断: 需要 subagent 吗?
    ↓
YES → 先启动对应 subagent → 收到结果 → 继续
NO  → 直接执行（仅限简单任务）
```

## 1. Effort Scaling（复杂度判断）

根据任务复杂度自动决定调度策略：

| 复杂度 | 特征 | 策略 |
|--------|------|------|
| **简单** | 单文件修改、明确的小改动 | 主 agent 直接做，不用 subagent |
| **中等** | 跨 2-5 个文件、需要理解上下文 | 1-2 个 subagent，串行 |
| **复杂** | 新功能、架构变更、涉及多模块 | 3+ subagent，尽量并行 |
| **大型** | 完整产品、重大重构 | 分阶段，每阶段独立调度 |

## 2. 自动触发规则

### Phase 0: 需求理解
| 触发条件 | Agent/Skill | 模型 |
|----------|-------------|------|
| 「写 PRD」「产品需求」「新功能规划」 | `/prd-writer` skill | - |
| 需要竞品/市场调研 | `Explore` + WebSearch | haiku |
| 「这个项目是干什么的」「帮我理解代码」 | `Explore` | haiku |

### Phase 1: 规划
| 触发条件 | Agent | 模型 |
|----------|-------|------|
| 实现新功能、添加新模块 | `planner` | sonnet |
| 系统设计、架构决策 | `architect` | opus |
| 深度分析现有功能 | `feature-dev:code-explorer` | sonnet |

### Phase 2: 实现
| 触发条件 | Agent | 模型 |
|----------|-------|------|
| 设计功能架构蓝图 | `feature-dev:code-architect` | sonnet |
| 构建失败、类型错误 | `build-error-resolver` | haiku |
| 写 system prompt、设计 LLM 交互 | `prompt-writer` | sonnet |

### Phase 3: 质量保证（可并行）
| 触发条件 | Agent | 模型 | 并行组 |
|----------|-------|------|--------|
| 代码写完，准备提交 | `code-reviewer` | sonnet | A |
| 涉及认证/支付/用户数据 | `security-reviewer` | sonnet | A |
| 需要补测试 | `test-creator` | sonnet | B |
| 清理死代码、重复代码 | `refactor-cleaner` | haiku | B |

### Phase 4: 验证
| 触发条件 | Agent | 模型 |
|----------|-------|------|
| 准备让用户测试前 | `e2e-runner` | sonnet |
| 更新文档/codemaps | `doc-updater` | haiku |

## 3. 并行调度规则

### 可以并行的组合
```
✅ code-reviewer + security-reviewer    # 同时审查
✅ test-creator + refactor-cleaner      # 互不影响
✅ Explore (多个不同目标)               # 各查各的
✅ doc-updater + code-reviewer          # 文档和代码独立
```

### 必须串行的依赖
```
❌ planner → 必须等规划完 → 才能写代码
❌ 写代码 → 必须等写完 → 才能 code-reviewer
❌ build-error-resolver → 必须等修复 → 才能继续
```

### 并行调度示例
```python
# 代码写完后，同时启动多个 reviewer
Task(subagent_type="code-reviewer", prompt="...", run_in_background=False)
Task(subagent_type="security-reviewer", prompt="...", run_in_background=False)
# ↑ 在同一条消息里发送，自动并行
```

## 4. Task Decomposition 原则

给 subagent 的 prompt 必须包含：

```markdown
## Objective（目标）
[一句话说清楚要做什么]

## Context（上下文）
[相关文件路径、已知信息]

## Output Format（输出格式）
[期望的输出结构]

## Boundaries（边界）
[明确说"不要"做什么，避免越界]
```

**Bad Example ❌**
```
"帮我 review 这个代码"
```

**Good Example ✅**
```
"Review src/auth/ 目录下的认证代码：
- 重点检查：SQL 注入、XSS、密码处理
- 输出格式：问题列表 + 严重程度 + 修复建议
- 不要：修改代码，只报告问题"
```

## 5. 模型选择指南

| 场景 | 模型 | 原因 |
|------|------|------|
| 快速搜索、简单分析 | `haiku` | 快 + 便宜 |
| 代码生成、review、测试 | `sonnet` | 平衡性能和成本 |
| 架构决策、复杂推理 | `opus` | 最强推理能力 |

**默认策略**：不指定模型时继承主 agent 的模型。

## 7. 错误处理

| 情况 | 处理方式 |
|------|----------|
| Subagent 超时 | 报告用户，询问是否重试 |
| 构建失败 | 自动启动 `build-error-resolver` |
| Review 发现严重问题 | 暂停流程，修复后重新 review |
| Agent 结果冲突 | 汇总给用户，让用户决定 |

---

## 8. 用户交互点

在以下节点**主动询问用户**：

1. **规划完成后** → "这是实现计划，要继续吗？"
2. **发现严重问题** → "发现 X 个高危问题，先修复还是继续？"
3. **阶段完成时** → "Phase X 完成，进入下一阶段？"
4. **有多个方案时** → "有 A/B 两种方案，你倾向哪个？"

**不需要询问**：
- 简单任务直接做
- 自动触发的 reviewer（做完汇报结果即可）
- 后台运行的 agent
